Two distinct buckets remain:

  - ROOT CAUSE (actionable, ~72 errors): **member types of an interface are not made implicitly `public` and `static`** (JLS 9.5). Every remaining vert.x case is a nested type of a `public interface`: `Executor.Action` (x27), `AltSvc.ListOfValue` (x11) / `AltSvc.Value` (x5), `HttpConfigurator.Http1x` (x11) / `H2` (x10) / `Http1XOr2Configurator` (x4), `PoolConnector.Listener` (x4). `SourceIndexer.modifierFlags` records only explicit source modifiers (so a bare `interface Action {}` → modifiers 0), and `IndexAccessFlags.classFlags` (source branch) never applies the interface-member rule. `fieldFlags`/`methodFlags` already apply the analogous implicit-`public` rule for interface-owner members, but there is no equivalent for nested TYPES. Result: the synthesized inner ClassSymbol is package-private (and non-static), so javac reports "not public … cannot be accessed from outside package" for both same-package AND cross-package uses. (Bytecode-indexed inners are unaffected: `ClassFileIndexer.visitInnerClass` already merges PUBLIC/STATIC from the InnerClasses attribute.)

    Plan:
    1. Add an `IndexAccessFlags` helper, e.g. `innerClassFlags(TypeEntry outer, TypeEntry inner)`, that computes `classFlags(inner)` and, when `inner.isSourceEntry()` and the OUTER entry is interface-like (`declKind` INTERFACE/ANNOTATION, or `modifiers & ACC_INTERFACE` for bytecode), ORs in `ACC_PUBLIC | ACC_STATIC`. Mirrors the existing source-only `fieldFlags`/`methodFlags` precedent; idempotent for bytecode.
    2. Call it from `IndexClassReader.readInnerClassesFromIndex` (the outer `c`/`entry` is in scope there) instead of the bare `IndexAccessFlags.classFlags(innerEntry)` at the `member.flags_field = innerFlags` site. Setting STATIC also fixes the enclosing-type wiring just below it (the `(innerFlags & ACC_STATIC)==0` branch must NOT run for interface members).
    3. Tests: (a) a `java-indexing` source-indexing unit test asserting `Executor$Action` gets PUBLIC|STATIC; (b) an `IndexCompileTest`-style compile test that opens `CombinerExecutor` (same package) and `SynchronizationTest` (different package) against a source index of `Executor` and asserts NO `not.def.public.cant.access`; (c) regression-check via the LSP diagnostics harness on vert.x.

  - OUT OF SCOPE / noise (~34 errors): `result is not public in java.util.concurrent.CompletableFuture` — all in `.metals/out/java.base/java/util/concurrent/CompletableFuture.java`, i.e. metals-extracted JDK source that the harness walked. When that file is compiled, references to the enclosing type's own package-private `result` bind to the INDEXED java.base binary `CompletableFuture` (whose member is package-private in a different package/module symbol) rather than to the source class being compiled — a self-shadowing artifact specific to compiling a file that duplicates an indexed type. Recommend excluding `.metals/out` (and similar caches) from the workspace walk; track the self-shadowing behavior separately if it ever affects real workspace sources.
