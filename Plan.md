## P4–P10 results (this pass)

Whole-workspace vert.x diagnostics dropped **748 → 272 total errors** and **147 → 30 files with errors** after the fixes below. The remaining tail is dominated by **P7** (Jackson 3 `tools.jackson.*` / `JsonTokenId` / `HybridJacksonPool` absent from the index classpath) and `module-not-found` (`module-info.java`), both environmental / out of scope.

Two infrastructure fixes were needed before the language fixes could even be measured:

- **Silent compile failures made visible.** `JavaTextDocumentService.refreshCompile` ran the compile on `CompletableFuture.runAsync` but only caught `RuntimeException`. javac signals fatal failures with `Error` subtypes (`com.sun.tools.javac.util.Abort`, `AssertionError`) and deep cycles with `StackOverflowError`; these escaped the catch, killed the async task, and published **no** diagnostics at all — the client just saw an indefinite hang. Widened the catch to `RuntimeException | Error` (and `logException(Throwable)`) so every compile failure surfaces as a `compiler-internal-error` diagnostic. This is what turned an opaque 120s timeout into the actionable `IllegalAccessError`/diagnostics below.
- **Diagnostics harness hygiene.** `LspWorkspaceDiagnosticsMain` now skips build/cache output dirs (`.metals`, `target`, `build`, `out`, `bin`, …) so self-shadowing metals-extracted JDK sources (a second `java.lang.Object`, etc.) no longer pollute or stall the measurement, plus a `diag.filter` substring selector and an on-timeout thread dump for diagnosis. NOTE: the run must be launched with the `--add-exports jdk.compiler/...=ALL-UNNAMED` flags (via `MAVEN_OPTS` for `exec:java`); without them the first compile throws `IllegalAccessError` on `com.sun.tools.javac.api.JavacTool`.

- [x] P4 — Types wrongly resolved to phantom java.lang.* · was 105 / 20 / 40 (`incompatible types: java.lang.Stream / java.lang.ReportMode / java.lang.Handler … cannot be converted to <real fqn>`).
  - ROOT CAUSE: `TypeRefResolver.resolveSimple` resolved an `Unresolved` (bare simple-name) leaf only against the compilation unit's imports/package, then fell back to `java/lang/<Name>`. It never applied JLS 6.5.5.1 step 1 — match the simple name against **member types in scope**: the enclosing type's own nested types, those **inherited** from its supertypes, and (recursively) the same for every **lexically-enclosing** type. So an inherited/sibling-scope nested type (e.g. `ReportMode` inherited from a base, `Stream` as a sibling member) silently became `java.lang.ReportMode` / `java.lang.Stream`.
  - FIX: added `findMemberTypeInScope` — walk outward through the lexical scope and, at each level, search the type and its transitive supertypes (`findInheritedMemberType`, cycle-guarded) for a nested type whose simple name matches, before the import/`java.lang` fallbacks. Supertype simple names are resolved via a dedicated `resolveSupertypeSimpleName` (siblings/single-import/same-package/on-demand, no `java.lang` fallback) so the walk stops cleanly instead of chasing a phantom. The walk is gated to source enclosing entries (bytecode leaves are always `Resolved`) and memoized per `(enclosing, simple)` — both correctness-neutral and a large perf win. Tests: `inheritedMemberTypeInIndexedSignatureResolves`, `siblingNestedTypeInIndexedSignatureResolves`.
